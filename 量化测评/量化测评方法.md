# game_planning_studio A2A 量化测评方法

> 目的：为简历「多智能体协作系统（A2A）」条目补上真实可复现的量化数字——**端到端任务完成率、任务流转成功率**。
> 原则：所有数字必须真实可复现（保留测试集、事件日志、原始方案副本），严禁编造；面试被追问时要能当场打开证据。
> 范围口径（2026-09-03 与梁志彬确认锁定）：**只测 A2A 主链路；同机双进程跑批；玩法策划必须在线；不做自动重试；本次不测跨机、不测玩法策划离线降级分支**。
> 模型与采样参数（两端独立，按各自生产配置，**不统一**）：主策划 lead_agent = **DeepSeek-V3.2，temperature 0.7**（该模型支持较高采样）；玩法策划 gameplay_agent = **Qwen3.6-Plus，temperature 0.4**（官方建议 0.3~0.5 更稳定，取中值）。量化测评复现的是"生产配置下的真实系统表现"，温度按各模型推荐值独立设置才具代表性；强行统一会使某一端工作在非推荐参数下，产生不代表真实水平的失败或漂移。

## 一、指标定义与口径

| 指标 | 分子 | 分母 | 备注 |
|---|---|---|---|
| **端到端任务完成率** | 主策划方案落盘 → A2A `tasks/send` 返回 `completed` → 玩法方案 artifacts 回传并写盘成功，全部走通的请求数 | runner 实际发起的请求总数（每条 1 个 run_id） | 任一环节失败即不算完成 |
| **任务流转成功率** | A2A 递交返回 `completed` 的递交次数 | A2A 递交尝试总次数 | 本次每条只递交 1 次，与端到端分母相同 |
| **阶段漏斗（辅助定位）** | 各阶段成功数 | 进入该阶段的请求数 | 主策划生成 / 递交 / 玩法生成 / 成果回传 四段 |
| **全程耗时** | — | — | min / avg / max，事件日志自带时间戳 |
| **方案结构完整率（可选，默认加）** | 玩法方案含全部必检章节的方案数 | 生成成功的方案数 | 本地规则检查，零 LLM 成本 |

### 失败分类（每条失败必须归类记录）
1. `lead_plan_fail`：主策划 LLM 调用异常（lead 侧 invoke 需包 try/except，现状会直接崩进程）
2. `a2a_failed_discovery`：玩法策划探活失败（不在线 / Agent Card 拉取失败）——测试前置已探活，出现即记录
3. `a2a_failed_offline`：递交时连不上玩法策划（ConnectionError）
4. `a2a_failed_jsonrpc`：JSON-RPC 返回 error
5. `a2a_failed_state`：返回 Task 但 `state != completed`
6. `task_failed`：玩法策划端 LLM 异常（gameplay 侧置 `failed`）
7. `artifact_missing`：状态 completed 但 artifacts 无文本（异常情况，单独盯）

## 三、执行步骤（埋点完成、服务就绪后）

```bash
# 1. 启动玩法策划（终端 1，监听 8080）
cd gameplay_agent
uv run python main.py

# 2. 探活（终端 2，确认在线再跑批）
curl http://localhost:8080/health
curl http://localhost:8080/.well-known/agent.json

# 3. 跑批（在项目根目录执行；runner 内部会再探活一次，不在线则整批中止）
cd ..
uv run --project lead_agent python 量化测评/run_e2e_batch.py

# 4. 查看产物
量化测评/量化测试报告_<YYYYMMDD>.md   # 汇总报告
量化测评/runs/<run_id>/               # 每条样本的方案副本（证据）
lead_agent/logs/events.jsonl          # 主策划端事件
gameplay_agent/logs/events.jsonl      # 玩法策划端事件
```

## 四、证据留存（可复现要求，指南红线）

1. **测试集**：`e2e_cases.yaml` 固定留存，含 20 条输入 + 预期结构检查点
2. **原始日志**：两端 `logs/events.jsonl`（含时间戳、失败原因、耗时、模型/温度）
3. **方案副本**：每条样本两份方案存档 `runs/<run_id>/`（主策划方案 + 玩法策划方案），防止 output/ 覆盖
4. **报告头部元数据**：测试日期 / 机器配置 / 两端模型与温度（lead=DeepSeek-V3.2@0.7、gameplay=Qwen3.6-Plus@0.4）/ 测试集路径 / 启动方式——数字只对"该元数据下的观测"负责，换模型或改温度后需重新出数，不得沿用旧数

## 附录 B：事件 schema（metrics.py 统一格式）

```json
{
  "ts": "2026-09-03T17:30:00.123+08:00",
  "agent": "lead_agent",
  "run_id": "uuid-1",
  "task_id": "uuid-2",
  "event": "a2a_completed",
  "state": "completed",
  "latency_ms": 48231,
  "error": "",
  "model": "deepseek-v3.2",
  "temp": 0.7
}
```

注 1：`model` / `temp` 为事件所属 Agent 的实际配置值——lead 端事件为 `deepseek-v3.2 @ 0.7`，gameplay 端事件为 `qwen3.6-plus @ 0.4`，两端不同属预期，字段按端如实记录。
注 2：`run_id` 在 lead 收到每条需求时生成；A2A 调用另生成 `task_id` 并记录绑定；gameplay 端事件用收到的 `task_id` 打点。归并键：端到端样本用 `run_id`，任务级事件用 `task_id`。
